# 注入的生命周期

宿主网页决定元素何时出现、何时被替换，Makoo 无法控制。本页解释 Core 如何在这种环境下安排一次挂载、判断它何时失效，以及失效后如何收尾和恢复。术语见[核心概念](./concepts.md)。

## 注入与执行

一个注入从 `apply()` 登记开始，到 `remove()` 成功结束，期间可能经历多轮**执行**：

- **组件执行**：从查找挂载目标开始，到这一轮的组件、容器和附属监听全部清理完毕为止。
- **监听执行**：一次查找监听目标、绑定事件、直到解绑的过程。

注入本身长期存在，持有声明、名称、命令入口和状态入口；每一轮执行只负责自己这一轮的 DOM 和资源。停止、整体重注入都是「结束这一轮，按需开始下一轮」，入口始终不变，所以组件和外部代码拿到的入口一直可用。

## 一轮组件执行

```text
start()
  ↓ 状态 waiting
查找挂载目标（等待预算 timeout，默认 15 秒）
  ↓ 找到第一个匹配元素
在挂载目标末尾创建组件容器 → 适配器挂载组件
  ↓ 挂载返回
启动全部附属监听（各自查找目标）
  ↓ 状态 mounted
持续检查挂载目标与组件容器是否仍然有效
```

几个要点：

- 目标已经存在时会立即找到；不存在时，Core 在页面 DOM 变化时重新检查，直到找到或超时。
- 每次查找都有独立的预算，页面上普通的 DOM 变化不会重置倒计时。超时后这一轮以 `MAKOO_TARGET_WAIT_TIMEOUT` 失败，不会自动重试。
- Core 只使用第一个匹配的元素，之后出现的其他匹配元素不会被处理。
- `mounted` 表示适配器的挂载调用已经返回，不代表框架已经完成首次渲染；React 的首次提交通常稍后才发生。
- 挂载返回后、每启动一个附属监听后，Core 都会立即再检查一次挂载目标和组件容器，不等下一次 DOM 变化。
- 组件进入 `mounted` 时，附属监听可能仍在 `waiting`。组件可以据此显示「等待网站按钮加载」之类的提示。

## 什么算失效

找到挂载目标之后，Core 关注的是**这个元素本身**，而不再是选择器：

- 挂载目标离开页面（包括它的某个祖先被移除）时，这一轮失效。
- 组件容器被移除，或被移出挂载目标时，这一轮失效。
- 挂载目标的文字、属性、class 改变，即使它不再匹配原选择器，也不算失效。
- 在同一批 DOM 变化中被移除又插回、最终仍然有效的元素不会触发重建。

监听目标同理：它离开页面时，这一轮监听执行失效。

## 收尾的顺序

一轮组件执行结束时，无论原因是什么，Core 都按同一顺序收尾：

1. 让这一轮失效：停止查找和失效检测，晚到的回调不再生效。
2. 停止全部附属监听，解绑它们的事件。
3. 调用适配器同步卸载组件。
4. 移除组件容器。
5. 汇总这一轮的结束原因、执行错误和清理错误。

某一步失败时，其余能执行的步骤仍会执行，尽量释放已经创建的资源。收尾完成之前，下一轮不会开始，所以不会出现新旧两个组件同时存在的情况。

## 结束之后

| 这一轮如何结束 | 之后 | 状态 |
| --- | --- | --- |
| 调用 `stop()`，清理成功 | 保留登记，等待再次 `start()` | `idle` |
| 调用 `remove()`，清理成功 | 注销，名称释放 | `idle` |
| 目标失效，开启了 `reinject` | 自动开始下一轮，重新查找挂载目标 | `waiting` |
| 目标失效，未开启 `reinject` | 停止，`lastError` 为 `MAKOO_MOUNT_TARGET_DETACHED` | `failed` |
| 执行失败（超时、挂载失败等），清理成功 | 停止，不自动重试，可以手动 `start()` | `failed` |
| 任何原因，但清理失败 | 关闭注入，拒绝再次启动 | `failed` |

处于执行失败的 `failed` 时调用 `stop()`，状态变为 `idle`，`lastError` 保留到下一次 `start()`。

适配器挂载抛错不一定是可重启的执行失败：适配器报告挂载失败后也无法释放干净时（例如 Vue 子组件在 `setup` 中抛错），按清理失败处理，注入被关闭。

### 整体重注入与局部恢复

`reinject` 同时控制两种恢复，范围不同：

- **整体重注入**：挂载目标或组件容器失效时，结束整轮执行（组件被卸载，组件内部状态随之丢失），再从查找挂载目标重新开始。
- **局部恢复**：某个附属监听的目标失效时，只重新查找并绑定这一个监听。组件和其他监听保持原样，该监听的状态在恢复期间是 `waiting`。

附属监听的任何执行失败都会以 `MAKOO_ATTACHED_LISTENER_FAILED` 结束整个组件：首次等待超时、绑定失败、局部恢复超时，以及未开启 `reinject` 时目标失效。这一结束不会触发整体重注入，即使组件开启了 `reinject`。附属监听是组件功能的一部分，缺了它组件不应继续假装可用。

独立监听用自己的 `reinject` 决定是否恢复，失败只影响它自己。

## 控制意图

`start()` 和 `stop()` 表达的是**意图**，Core 只执行最新的意图：

- 快速连续切换启动和停止，不会累积多次启动。
- 正在清理时调用 `start()`，只有这一轮因 `stop()` 或「目标失效且开启了 `reinject`」而结束、并且清理成功时，才会接着开始下一轮。因执行失败结束时，这个启动请求被丢弃，状态停在 `failed`。
- 适配器挂载期间调用 `stop()`，挂载一返回就直接收尾，不会启动附属监听。
- `remove()` 会取消尚未执行的启动请求。

## 为什么清理失败会关闭注入

清理失败意味着 Core 无法确认页面上没有残留的组件、容器或事件绑定。如果这时允许重启，新一轮可能叠加在残留资源上，造成重复挂载、事件触发两次。这类问题比「功能停了」更难察觉和定位。

因此清理失败的注入会停在 `failed`：保留诊断，继续占用名称，拒绝 `start()`（`MAKOO_INJECTION_CLOSED`；实例已经 `dispose()` 时为 `MAKOO_INSTANCE_DISPOSED`）。重复的 `stop()`、`remove()` 或 `dispose()` 返回同一个失败结果，不会再次尝试清理。修复问题后刷新页面即可。其他注入不受影响。

普通执行失败不在此列：只要清理成功，就可以再次启动。

## 谁负责清理什么

| 资源 | 负责方 |
| --- | --- |
| 目标查找、失效检测、组件容器 | Core |
| 附属监听和独立监听的事件绑定 | Core |
| 组件的挂载与卸载 | 适配器 |
| 组件内的状态订阅（通过 Makoo API 建立的） | 适配器，组件卸载时释放 |
| 组件自己创建的定时器、全局事件、请求、插入 `body` 的节点 | 组件，在框架的卸载钩子中释放 |

Core 不会中断已经开始执行的事件处理函数，也不会回滚它的业务副作用；解绑只保证之后不再调用它。
