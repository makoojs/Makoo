# Fill the gap with Instance Observation instead of restoring ObserverHub

Item 3 (hooks and external observers) decides: the current phase of a single Injection continues to be observed only through Status Handle / StateView; Core Instance gains a closed, read-only `observe` that synchronously delivers a small set of Observation Notices (`injection-removed`, `instance-disposed`, `diagnostic`) after facts are committed. The old `createObserverHub` / `ObserveEvent` event bus is not restored, no user lifecycle hooks are provided on declarations, and `observe` is not exposed to mounted components.

This path was chosen because the old Hub pushed the lifecycle into an emittable, interceptable parallel narrative that could easily become a second scheduler; the new Core internally already uses direct domain calls + `status.set`, and externally only needs to add the instance-level facts that Status Handle cannot express. `observe` callbacks are allowed to synchronously re-enter `command` / `remove` / `dispose`, but facts must be committed before notifying, a snapshot of subscribers must be used, a single dispose produces only one `instance-disposed`, and diagnostics must not nest infinitely; observation must not become Core's scheduling engine. Getting-started docs use `statusHandle` / `command` as the main path, leaving `observe` to advanced scripts and the CLI.
